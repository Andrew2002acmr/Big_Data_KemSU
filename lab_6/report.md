# Лабораторная работа № 6. DevOps для Big Data

Вариант 6

## Цель

Развернуть стенд обработки данных о повторных госпитализациях и снизить расчётную стоимость пакетного задания Spark минимум на 35 %. Для сервиса оценки риска заданы p95 до 50 мс, доступность от 99,9 % на нагрузочном тесте и FPR до 1 %.

## Стенд

Docker Compose запускает kind с тремя узлами. Spark Operator выполняет пакетную агрегацию, Flink Operator запускает поток Kafka → Flink → Redis. Kafka и Redis используют StatefulSet и PVC. Сервис модели распределён по двум стабильным узлам. Spark предпочитает узел с меткой `spot` и может запустить исполнителя на стабильном узле. KEDA меняет число реплик по отставанию Kafka, Spark выделяет от одного до двух исполнителей.

Исходный CSV прошёл 5 из 5 проверок Great Expectations. Контрольная запись с неверной меткой была отклонена. DVC восстановил CSV с той же контрольной суммой. Delta Lake вернул версии 0 и 1 с итогами 30 000 и 30 001 строк. FPR ONNX-модели на отложенной выборке предыдущей лабораторной составил 0,646 %.

## Стоимость обработки

В обоих профилях Spark агрегировал 720 000 строк и вернул одинаковые значения для девяти групп. Ставку одного инстанса умножили на сумму секунд работы исполнителей из Spark event log. Расчёт относится к исполнителям по тарифам EC2 On-Demand.

| Профиль | Ядра / heap исполнителя | Время задачи, с | Исполнители, с | Цена задания, $ |
| --- | --- | ---: | ---: | ---: |
| `m6i.xlarge` | 2 / 1 536 МБ | 24,47 | 26,104 | 0,001392 |
| `m6i.large` | 1 / 768 МБ | 24,18 | 24,772 | 0,000661 |

**Расчётная экономия составила 52,55 %** при цели 35 %. Многоэтапная сборка сократила размер образа модели с 769,0 до 336,2 МБ, на 56,3 %.

## Нагрузка и отказ узла

| Режим | Целевые запросы/с | Успешно | p95, мс | p99, мс |
| --- | ---: | ---: | ---: | ---: |
| Обычный | 50 | 1 500 / 1 500 | 41,24 | 137,01 |
| Пиковый | 100 | 1 500 / 1 500 | 36,58 | 116,17 |
| Spot-узел выключен | 100 | 1 200 / 1 200 | 6,87 | 59,03 |

За три прогона доступность HTTP составила 100 %. В тесте отказа контейнер spot-узла был остановлен на весь прогон. Spark потерял исполнителя, создал замену и завершил агрегацию. Этот прогон исключён из расчёта стоимости.

После отправки 1 400 сообщений KEDA подняла число готовых реплик с двух до четырёх. После обработки очереди осталось две реплики. Тестовое событие прошло через Kafka и Flink до Redis, время завершённого checkpoint составило 1,792 с.

## Деплой и мониторинг

Генератор отправлял 5 % запросов на canary. Версия v2 прошла 10 из 10 проб и была развёрнута как основная. Версия v3 вернула HTTP 503 на всех 10 пробах. После удаления canary все 100 контрольных запросов обработала версия v2 с p95 2,28 мс.

В Prometheus и Grafana собраны CPU, память, сеть, Spark spill, время checkpoint и качество данных. Spark записал 0 байт spill. При искусственном сдвиге BMI измеренный PSI достиг 8,764, и Prometheus активировал `HighDataDrift` при пороге 0,2. При таком алерте продвижение версии приостанавливают и проверяют входные данные. Метрики сохранены в MLflow.

## Дополнительные профили

CapacityScheduler для YARN задаёт доли очередей 60/30/10. Для AWS подготовлен профиль Cluster Autoscaler. GPU-профиль выделяет один NVIDIA GPU на исполнитель и четверть GPU на задачу через RAPIDS. При ставках $0,096/ч для CPU и $0,526/ч для GPU CPU-задача на 30 с стоит $0,00080. Для окупаемости GPU должен завершить её менее чем за 5,48 с, включая 2,5 с инициализации. На kind используется CPU-профиль, YARN и облачный автоскейлер описаны конфигурациями.

## Вывод

Локальный стенд выполнил цели по стоимости, доступности и p95. Для промышленного запуска потребуется проверить доступность на длительной нагрузке, отказ стабильного узла и качество модели на реальных данных. Полнота модели на синтетической выборке составила 0,54 %.
